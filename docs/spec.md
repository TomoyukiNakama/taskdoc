# TaskDoc 仕様書（ドラフト）

> 状態: 策定中。「未決定」の項目は今後決める。

## 1. 概要

タスクとドキュメントを紐づけて管理するアプリケーション。

- クライアント: Avalonia UI 12.0.x（現在 12.0.5。12.1 以降は .NET 8 SDK のコンパイラーに対応しないため。デスクトップ / ブラウザ(WASM) / Android / iOS）、および WPF 版（Windows 専用、WPF-UI 4.x）。ViewModel と API 通信は共通ライブラリ（TaskDoc.Client）にまとめ、両方で使う
- サーバー: ASP.NET Core Web API（同一ソリューション）
- ランタイム: .NET 8（LTS）。ただしブラウザ版・Android・iOS は Avalonia 12 の要件により .NET 10
- 通信: 常にオンライン（クライアントはデータを持たず、毎回 API を呼ぶ）

## 2. 技術方針

| 項目 | 方針 |
|---|---|
| データベース | SQLite（当面）。将来の変更に備え、SQL はリポジトリ層に閉じ込める |
| データアクセス | Dapper + Microsoft.Data.Sqlite（EF Core は使わない） |
| スキーマ管理 | DbUp（`dbup-sqlite`）。番号付き SQL ファイルを API 起動時に順番に適用する |
| API の形式 | ASP.NET Core Minimal API |
| MVVM | CommunityToolkit.Mvvm |
| UI テーマ・部品 | Avalonia 版: [ShadUI](https://github.com/accntech/shad-ui)（shadcn/ui 風、MIT）。FluentTheme は使わない。アイコンは Lucide（ISC、`Assets/Fonts`）。WPF 版: [WPF-UI](https://github.com/lepoco/wpfui)（Fluent、MIT）。アイコンは WPF-UI 付属の Fluent System Icons |
| API クライアント | Refit（Contracts の DTO をそのまま使う） |
| リアルタイム通信 | SignalR |
| テスト | xUnit v3（3.2.x。Avalonia.Headless.XUnit 12 が 4.x に未対応のため）。API は一時 SQLite ファイル、UI は Avalonia Headless でテストする |
| バージョン管理 | git（CI は当面なし） |
| 共有コード | API とクライアントで DTO（TaskDoc.Contracts）を共有。Avalonia 版と WPF 版で ViewModel・API クライアント・ログイン状態の管理（TaskDoc.Client）を共有 |
| iOS ビルド | macOS + Xcode が必要（開発機は Ubuntu のためビルド対象外） |
| サーバーの実行環境 | 未定。特定の OS やホスティングに依存しない作りにする（設定は環境変数 / appsettings で切り替え） |
| 画面の言語 | 日本語。文言はリソースファイルに分け、将来ほかの言語を追加できるようにする |

## 3. ユーザーと認証

### 3.1 ユーザーの種類

| 種類 | 認証方法 |
|---|---|
| AD ユーザー | 社内のオンプレミス Active Directory に LDAP で問い合わせる |
| システムユーザー | システムの DB に保存したパスワードハッシュと照合する |

- **どちらの種類も、システムの DB に登録済みのユーザーだけがログインできる。**
  - AD で認証できても、DB に登録されていなければログインを拒否する（自動登録しない）。

### 3.2 ログインの流れ

1. クライアントでユーザー名とパスワードを入力する
2. API がユーザーの種類に応じて AD またはDBで確認する
3. 成功したら API が JWT を発行し、以降の API 呼び出しはそのトークンで認証する

### 3.3 認証の詳細（実装済み）

| 項目 | 内容 |
|---|---|
| ユーザー名 | 大文字小文字を区別しない。`user` / `DOMAIN\user` / `user@domain` のどれで入力しても `user` として扱う。半角英数字と `. _ -` で 1〜64 文字 |
| アクセストークン | JWT（HMAC-SHA256）、有効期限 15 分 |
| リフレッシュトークン | 有効期限 14 日。使うたびに新しいものに交換する。使用済みのトークンが再び使われたら盗用とみなし、そのユーザーの全セッションを無効にする。DB にはハッシュだけを保存する |
| パスワード（システムユーザー） | PBKDF2-SHA256（60 万回）で保存。8 文字以上 |
| ロックアウト | 5 回続けて失敗すると 15 分ロック（AD ユーザーにも適用し、AD 側のロックを誘発しにくくする） |
| AD 接続 | LDAPS（636）で `アカウント名@ドメイン` として bind する。サーバー・ポート・ドメインは設定ファイルで指定 |
| AD に接続できないとき | 「認証サーバーに接続できません」と表示する（503） |
| 初期管理者 | ユーザーが 1 人もいないとき、API 起動時にシステムユーザー `admin` をランダムなパスワードで作成し、ログに 1 回だけ出力する。設定 `Auth:InitialAdmin:Password` があればそのパスワードで作成し、ログには出さない（8 文字未満なら起動を失敗させる） |
| 署名鍵 | 本番では環境変数 `Auth__Jwt__SigningKey`（32 文字以上）が必須。開発環境で未設定なら起動ごとに一時的な鍵を使う |
| クライアントのトークン保存 | メモリのみ。アプリを起動するたびにログインが必要 |

- 管理者は、ユーザーの登録（システムユーザー / AD ユーザー）、表示名・メール・管理者フラグ・有効/無効の変更、システムユーザーのパスワード再設定ができる。
- 有効な管理者が 0 人になる変更はできない。
- ユーザーを無効にする、またはパスワードを変更すると、そのユーザーのリフレッシュトークンをすべて無効にする。発行済みのアクセストークンは期限（最大 15 分）まで使える。
- システムユーザーは自分のパスワードを変更できる。AD ユーザーのパスワードは AD で管理する。

### 3.4 画面（実装済み）

| 画面 | 対象 | 内容 |
|---|---|---|
| ログイン | 全員 | ユーザー名とパスワードを入力。Enter でもログインできる |
| サイドバー | ログイン後 | ホーム / ユーザー管理（管理者のみ） / パスワード変更（システムユーザーのみ）、ログイン中のユーザー、ログアウト。折りたたむとアイコンだけになる（狭い画面向け） |
| ユーザー管理 | 管理者 | ユーザー一覧（ユーザー名・表示名・種類・権限・状態・最終ログイン）。登録、編集（ダブルクリックでも可）、システムユーザーのパスワード再設定。登録・編集はダイアログで行う（ブラウザ版・モバイルでも同じ操作）。狭い画面では一覧を横にスクロールする |
| パスワード変更 | システムユーザー | 現在のパスワードと新しいパスワード（確認入力あり）。変更後もこの端末はログインしたまま |

- 「登録しました」などの完了メッセージは、画面右下のトースト通知で表示する。
- 入力エラーやサーバーのエラーは、画面内の赤い警告枠で表示する。
- 色はライト/ダークとも ShadUI の配色に従い、OS の設定に合わせて切り替わる。

- 管理者は、自分自身の管理者権限と有効/無効を画面から変更できない（自分を締め出さないため。ほかの管理者が変更する）。
- API の入力エラー（ユーザー名の形式、パスワードの長さ、重複など）は、API が返す日本語のメッセージをそのまま表示する。

## 4. 権限

権限は次の 3 つの単位で設定・制御する。

1. **プロジェクト単位**: プロジェクトごとにメンバーと権限を設定する
2. **グループ単位**: システムで定義したグループに権限を設定する
3. **タスク単位**: 割り当てられたタスクごとに権限を設定する

- 権限は**操作ごとに細かく**許可する（ロールでまとめない）。
  - 操作の例: 閲覧 / 作成 / 編集 / 削除 / 担当者変更 / 状態変更 / ドキュメント編集 / コメント
- 3 つの単位の権限が重なったときは**許可を合算**する（どれか 1 つで許可されていれば操作できる。「禁止」の設定はない）。
- **システム管理者**はすべて操作できる（ユーザー・グループ・ワークフローの管理、すべてのタスクとドキュメントの操作）。
- 未決定: 操作の一覧の確定

## 5. ドキュメント

タスクに紐づけるドキュメントとして、次をすべて扱う。

| 種類 | 内容 |
|---|---|
| 外部リンク | URL や共有フォルダのパスを登録して参照する |
| アプリ内の本文 | アプリで書いたテキストを DB に保存する |
| ファイル | PDF / Word / 画像などを API 側に保存する |

- 本文とファイルは**更新履歴（版）を残す**。
- 本文は **Markdown** で保存する。リッチテキストに近い操作感にするため、次のようにする。
  - ツールバーのボタンで装飾（太字、見出し、リスト、リンクなど）を入力できる
  - 表示時は整形して見せる
  - Avalonia に標準のリッチテキストエディタがないため、見たまま編集（WYSIWYG）方式は採らない
- ファイルは **API サーバーのフォルダ**に保存し、DB には保存場所とファイル情報（名前、サイズ、種類、版）だけを持つ。
- 未決定: ファイルのサイズ上限、外部リンクの履歴の扱い

## 6. タスク

### 6.1 項目

| 項目 | 備考 |
|---|---|
| タイトル / 説明 | |
| 状態 | ワークフローに従って変わる（6.3） |
| 作成者 / 作成日時 / 更新日時 | |
| 担当者 | 複数可 |
| 開始日 / 期限 | |
| 優先度 | |
| 親タスク | サブタスクを作れる（親子関係） |
| タグ | 分類用 |
| コメント | タスクへのコメント欄 |
| 変更履歴 | 状態や担当者など、タスク自体の変更を記録する |

### 6.2 プロジェクトとの関係

- タスクはプロジェクトに**属さなくてもよい**（プロジェクトに属さない個人タスクを作れる）。
- 個人タスクは、**作成者が共有先（ユーザー / グループ）を設定**して共有できる。共有はタスク単位の権限で制御する。

### 6.3 状態とワークフロー

- 状態の種類に加えて、**遷移ルール**（どの状態からどの状態へ、誰が動かせるか）を定義する。
- ワークフローは**システムでテンプレートとして複数定義**し、プロジェクトごとに使うものを選ぶ。
- 個人タスクは既定のワークフローを使う。
- 未決定: 既定ワークフローの状態と遷移、プロジェクトのワークフローを途中で変更したときの既存タスクの扱い

## 7. 通知

| 種類 | 内容 |
|---|---|
| アプリ内通知 | 担当になった、コメントされた、状態が変わった、などをアプリ内の通知一覧に表示する |
| リアルタイム更新 | 他のユーザーの変更を、開いている画面にすぐ反映する（SignalR） |

- メール通知は行わない（当面）。
- 未決定: 通知のきっかけになる操作の一覧、既読管理

## 8. 検索

- タスクとドキュメント本文を**全文検索**できる。
  - SQLite の FTS5 を使う。日本語に対応するため trigram 方式にする（3 文字以上で検索）。
- 状態・担当者・タグ・期限などの条件での絞り込みもできる。
- アップロードしたファイル（PDF / Word など）の中身は検索対象にしない（当面）。
- trigram 方式は 3 文字未満の語を全文検索の索引で探せないため、2 文字以下の検索語は部分一致（LIKE）検索に切り替える。
